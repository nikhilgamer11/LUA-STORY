What is Anywhere Really?
Our Vision
Make the LMS Disappear.
LearnUpon Anywhere enables businesses to seamlessly integrate courses into any product experience — so learners never have to go elsewhere.
🎯
Meet learners where they are
Embed LearnUpon into any app, portal, or website. Training appears in the tool they already use.
⏱️
Right learning, right time
Serve content in context using SSO to streamline flows. Right people, right learning, right moment.
🛰️
LMS as mission control
Build in LearnUpon. Deliver everywhere. Track in one place. Admins manage everything as usual.
Two Implementation Options
You decide where, when, and how learning appears
Option 1
🚀 Grab & Go
LearnUpon provides a code snippet. Copy, paste, done. Static learning — same for everyone. No developer needed for basics.
Best for:
✓ Static learning content
✓ Quick embed with no personalisation
✓ Low or no dev resource available
Option 2
⚙️ Custom iFrame
You build the iFrame. You decide the where (profile page, training tab), the when (on login, on trigger), and the how (modal, inline, full-page).
Best for:
✓ Dynamic and personalised learning
✓ SSO + API + Webhook integration
✓ Real-time completions feeding back to your system
What powers the experience
APIs + Webhooks = a real-time learning layer
🔌
REST API
User provisioning and management. Group creation. Enrollment creation, reporting, marking complete. GET /courses · POST /enrollments · GET /enrollments/search
🔔
Webhooks
Two-way real-time data. Fires as events happen — no polling needed. Course published. Module completed. Learning path completed. Badge awarded.
🔐
SSO — SAML or SQSSO
Learner already authenticated. One click and they are in their course. forEmbed=true hides the LMS UI. redirect_uri sends them directly to their enrollment.

How Far Can It Go?
Before you scope a mobile deal
Three mobile app types. One question to ask first.
"How is your app built?" — ask this before anything else.
01
Native⚠️ Significant limitations
Built 100% in Swift (iOS) or Kotlin/Java (Android). No wrappers. Fully custom code.
Anywhere NOT natively supported. Requires a Webview. High dev effort. Test everything first.
02
Pure Hybrid (Wrapper)⚡ Minor limitations — fixable
Just enough native code to load on phone. The rest loads an external site — like LearnUpon — in a WebView wrapper.
Anywhere works well here. Video/audio download blocked, assignment recording needs a code fix.
03
Cross-Platform Hybrid⚡ Minor limitations — fixable
Mix of Native and JavaScript (React Native, Flutter). Uses a wrapper like Pure Hybrid.
Same as Pure Hybrid. Large dependency on developer competency. Test thoroughly before committing.
B
Desktop & Mobile Browser✅ Fully supported
Standard web browser on any device. No app architecture concerns.
Fully supported. All module types work. SCORM/xAPI works. Best starting point for most deals.

The honest conversation
Knowing the limits is what builds trust
✅
When to say yes confidently
Desktop browser or hybrid mobile app. Has SSO already set up. Has dev resource. Content is text, video, SCORM. Not relying on assignment recording on mobile.
⚡
When to scope carefully
Prospect says "mobile-first" — ask which app type first. Native app with no Webview planned. SCORM dispatched from external tool. Assignment recording required on mobile.
🔍
What to always ask
How is your app built — native, hybrid, or browser? How do users log in today? Do you have dev resource? What content types are you using?
⚠️
What kills deals silently
Promising full mobile support without knowing the app architecture. Not asking about SSO setup early. Demoing desktop only when they want mobile.

The Golden 24 Hours
Sarah said: "Your mobile demo changed everything — we've never seen training work on the shop floor before."
You have 24 hours. One email. Make it count.
Subject
Prove you heard them. Name their exact pain — not 'following up on our call'.
Opening line
Quote their words back. Not 'thanks for the time.' Use what they said.
Value
1 sentence. 1 screenshot. Their use case — not your feature list.
Next step
Specific date. Specific action. Not 'let me know if you have questions.'

Handle the Objection
Thursday 3:47pm · Technical SSO validation call
In call
Sarah Chen
NorthStar Retail
14 minutes in — going well
Then suddenly — IT joins the call...
🚨 Objection incoming
IT Manager — NorthStar
"Our IT policy blocks iFrame embedding on all external domains. This won't work."
Objection — IT policy
"iFrame embedding is blocked by our IT policy."
A
Acknowledge: "That's a really common first response from IT — and it makes sense they're cautious."
C
Contextualise: "Usually it's a default CSP header setting, not a hard block. We've resolved this in 3 calls with similar retail IT teams."
E
Evidence & Escalate: "We also support SQSSO deep links as an alternative. 20-minute call with your IT team this week — I'll have an answer by Friday."
✅
Objection handled
IT confirmed the CSP header was a default setting — not a hard block. SQSSO approach agreed. Technical validation: 1 week. Deal progressing.
ACE in action
Acknowledge
Never argue. Validate first. Drops defensiveness before you solve.
Contextualise
Reframe the real concern — effort and settings, not impossibility.
Evidence
Close with proof or a named next step. Never leave it hanging.
